## 작업 방식 (매번 지켜야 하는 규칙)
- 작업 시작 전에 설명하고 컨펌받은 뒤 구현
- 기능 하나 끝날 때마다 PR 만들지 먼저 물어보기 (자동으로 만들지 않기) — 단, PR을 머지할 때 딸려오는 브랜치 자동 삭제(`--delete-branch`)는 별도 확인 없이 진행
- 이미 머지된 코드에서 버그 발견하면 매번 `product-spec.md`의 B-11 섹션에 기록
- 새 개념 설명 전에 `docs/learning-notes.md` (사용자의 기존 학습 노트, gitignore됨) 먼저 확인, 중복 작성 금지
- 페어프로그래밍 스타일 — 코드는 작성하되 왜 필요한지 설명하면서 진행 (사용자가 Spring/Java 백엔드 학습 목적으로 이 프로젝트를 시작함)
- PR이 머지되면서 스택된 브랜치가 충돌 상태가 되면, force-push보다 "새 브랜치 이름으로 rebase본 올리고 기존 PR은 닫기" 방식을 우선 사용 (force-push는 매번 별도 승인 필요)

## 로컬 개발 환경 메모
- 백엔드: `cd backend && ./gradlew bootRun` (포트 8080). 실행 중인 프로세스 확인은 `lsof -i :8080`으로 — gradle daemon 특성상 `pkill -f 'gradlew bootRun'`으로는 실제 java 프로세스가 안 죽을 수 있음, PID 직접 kill 권장
- 프론트: `cd frontend && npm run dev` (포트 5173). **서비스워커는 개발 중 꺼둠**(`vite.config.ts`의 `devOptions.enabled: false`) — 켜두면 옛 번들을 캐시로 물고 있어서 코드를 고쳐도 반영이 안 된 것처럼 보인다. 푸시 알림을 로컬에서 직접 테스트할 때만 잠깐 켤 것
- DB: `mysql -h127.0.0.1 -P3307 -ucherry -pcherrypw1234 cherry -e "..."` (한글 조회 시 `--default-character-set=utf8mb4` 빠뜨리지 말 것)
- 로그인: 이제 실제 구글 계정으로 로그인해야 함(`/oauth2/authorization/google`). 세션은 DB에 저장되므로 백엔드를 재시작해도 로그인이 풀리지 않는다
- 테스트 중 실 계정의 포인트/인구/daily_stat을 건드렸다면 작업 끝나고 반드시 point_ledger 근거로 원상 복구할 것 — 이번 세션에서 몇 번 실수했던 부분
